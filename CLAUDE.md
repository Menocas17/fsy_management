# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FSY Management — a Rails app for managing participants (youth and staff) of an FSY event: registration, profiles, medical/contact info, stake/ward/room assignment, company staffing, and a KPI dashboard. UI copy, locale strings, and commit messages in this repo are in Spanish; code identifiers are in English.

## Commands

```bash
bin/dev                        # start web (rails server) + css (tailwind watch) + worker (solid_queue) — use this for local dev
bin/rails solid_queue:start     # worker only (required for preprocessed avatar thumbnails and deliver_later emails)

bin/rubocop --no-server        # lint (Rails Omakase style)
bin/brakeman --no-pager        # static security scan
bin/bundler-audit               # gem vulnerability scan
bin/importmap audit             # JS dependency vulnerability scan

bin/rails db:schema:load:queue  # load Solid Queue's separate queue DB schema (needed once per fresh DB; create it first with bin/rails db:create if it doesn't exist)
```

CI (`.github/workflows`) runs scan_ruby (brakeman, bundler-audit), scan_js (importmap audit), lint (rubocop), and test (Minitest against Postgres) on every PR/push to main — all must pass before deploy.

## Architecture

Module notes for Áreas de logística, Menú lateral, Notificaciones, Inventario, Registro, Asistencia nocturna and Deploy live in `.claude/rules/` and load when touching those files.

**Multiple databases:** the app connects to a `primary` DB plus a separate `queue` DB for Solid Queue (`db/queue_schema.rb`, `config/database.yml`). In development, cache/cable stay in-memory but queue is real — the worker (`bin/dev`'s `worker` process, or `bin/rails solid_queue:start`) must be running for avatar thumbnail preprocessing and background emails to actually process. Production instead puts primary/cache/queue/cable in one database (see `.claude/rules/deploy.md`); Solid Queue runs in-process with Puma (`SOLID_QUEUE_IN_PUMA`), no separate worker.

**Auth:** custom, not Devise. `has_secure_password` on `User` + signed-cookie sessions. `Authentication` concern (`app/controllers/concerns/authentication.rb`) handles session resumption/creation via `Current.session`/`Current.user`. An account must be the superadmin or linked to a participant (`User#linked?`); deleting a participant deletes its account, and an unlinked account can't sign in nor resume a session. Sessions end after 30 days idle or 90 days total (`Session`). Logged-in users change their password at `/contrasena/cambiar` (`PasswordChangesController`, requires the current one); the emailed reset (`PasswordsController#new/create`) is gated by `config.x.password_reset_emails`, on wherever mail can really go out (`MailDelivery.configured?`, `config/mail_delivery.rb`). Mail goes out over HTTPS through a Google Apps Script web app that sends from the publisher's Gmail (`:apps_script` delivery method, `lib/apps_script_delivery.rb`, script in `docs/apps_script/mail_relay.gs`, env `MAIL_RELAY_URL`/`MAIL_RELAY_SECRET`, ~100 recipients/day) because Render free blocks SMTP ports 25/465/587 and the free 2525 providers want a domain or a phone; SMTP (`config/smtp_mail.rb`, `SMTP_USERNAME`/`SMTP_PASSWORD`/`MAILER_FROM`, port 2525) stays as the fallback when the relay isn't set. In development mail only goes out with `CORREO_EN_DESARROLLO=1`; `bin/rails 'correo:prueba[a@b.com]'` sends a test. `filter_parameters` must keep `:passw`/`:email`. **Accounts** are created from a ficha's profile ("Crear cuenta" → dialog that asks for the email twice → `ParticipantAccountsController#create`) with a random password nobody sees; `PasswordsMailer.invitation` emails a link (`User#invitation_token`, `generates_token_for :invitation`, valid `User::INVITATION_VALID_FOR`, dies once the password changes) to `passwords#edit` to choose one. The same controller's `update` ("Restablecer contraseña") voids the password, closes the account's sessions and emails a new link. Never reintroduce a shared default password: the repo is public. If the ficha already has an email, the dialog offers it or another one; whichever is used is also written to the ficha (`save_email_on_ficha`, skipping the ficha's other validations). The profile's Contacto section shows "Todavía no entra" until `users.first_signed_in_at` is set by `SessionsController#create` (not session presence: signing out deletes the session). Who: `User#account_manager?` (superadmin, director, coordinador, director_logistica), narrowed by `Authorization#can_create_account_for?`/`can_reset_account_of?`: only full access touches a director's or coordinator's account, and nobody resets their own. Both actions write `AuditLog` category `cuentas`. `Authorization` concern (`app/controllers/concerns/authorization.rb`) handles role-based permissions — both view-level helper methods (`can_view_companies?`, `full_company_access?`, `can_edit_auxiliar_company?`, `can_edit_company?`, `can_manage_staff?`) and the strong-params allowlist (`allowed_participant_attributes`, used by `ParticipantsController#participant_params`) which grants fields based on the acting user's role.

**Domain model — participants and companies:**
- `Participant`: the core record (youth or staff). Contact/emergency/medical fields live in `jsonb` columns exposed via `store_accessor` (`contact_info`, `person_in_charge`, `medical_info`) rather than real columns. Avatar via Active Storage with `thumb`/`preview` variants, both `preprocessed: true` (see queue DB note above). Production has 512 MB: the browser downscales the photo to 1600 px before uploading (`avatar_preview_controller.js`), and `config/initializers/image_processing.rb` runs libvips with one thread and no cache and lets only one image analysis/variant job run at a time — a raw 12 MP phone photo is what ran the instance out of memory.
- `Company` / `AuxiliarCompany`: a two-level staffing hierarchy. An `AuxiliarCompany` is looked after by both `coordinador`-role participants (all of them, not chosen per branch: `AuxiliarCompany#coordinators`) and groups several standard `Company` records (`company.auxiliar_company_id`).
- `Membership`: polymorphic join (`associable`: `Company` or `AuxiliarCompany`) between a company and a `Participant`, carrying `role`/`gender` copied from the participant (kept in sync via `Participant#sync_membership_gender`). A unique index on `(associable_type, associable_id, role, gender)` enforces at most one man and one woman per role per company — this 1M/1F staffing template is a deliberate business rule, not an oversight.
- Role-scoped query helpers live on `Participant`: `auxiliar_companies_with_counselors` (coordinador's view), `auxiliar_scope` (auxiliar's AC + its counselors + their companies), `counselor_scope` (consejero's own company). `Authorization#can_edit_company?`/`can_edit_auxiliar_company?` consume these scopes to decide edit access — when changing staffing/permissions logic, both the model scope and the authorization concern usually need to change together.

**Role permission summary:** any authenticated user can view everything; editing always goes record by record through `Authorization` (`can_edit_participant?`, `company_edit_level`, `auxiliar_company_edit_level`), never through a blanket "is admin" check. Full access (`User#full_access?`: superadmin — the `users.superadmin` column, never inferred from a missing participant —, `director`, `coordinador`) edits every ficha and every company. `auxiliar`: the jóvenes of the companies in their branch, those companies (data + counselor staffing, but not moving them to another branch), and the name of their own auxiliar company. `consejero`: the jóvenes of their own company, plus its chosen name — nothing else, not its staffing nor its auxiliar company. `director_logistica`: their own committee (`logistica`/`director_logistica` fichas), including registering and deleting them. `logistica`: read-only, plus what its area's flags give (with `checkin`, `User#checkin_member?`, it registers and edits jóvenes, imports them and scans arrivals — the old `registrador` role, retired; its enum value 4 stays unused). Everyone may edit their own ficha, minus `rol`/`company_id`/`logistics_area_id`. `ParticipantsController#update` re-checks the scope *after* assigning attributes, so no one can edit a record out of their own reach. The side menu (`NavigationHelper#nav_sections`) lists only what the person can open — a module without access is omitted, never shown greyed out.

**Ver como** (`ViewAsController`, `/ver-como`): the superadmin picks a role from the account menu (`Participant.view_as_sample`, preferring a ficha with an account and someone to manage) or "Ver como" on a staff profile, and `Current.user` becomes that person (`Current.viewing_as`; `Current.real_user` stays the superadmin), so menu and permissions are exactly theirs. A ficha without an account gets a readonly stand-in (`User.stand_in_for`). Stored in `session[:view_as_participant_id]`, honored only for a superadmin session, cleared on sign in/out; password changes are blocked meanwhile and `record_audit!` logs the superadmin "(viendo como …)". `script/demo.rb` drives a read-only Selenium tour of every role through it, desktop and phone side by side (`bundle exec ruby script/demo.rb`, env vars documented at its top). A new feature or module gets a scene in `script/demo.rb` only when the request explicitly asks for it; otherwise leave the demo untouched.

**Entrar con huella** (passkeys / WebAuthn, gem `webauthn`): `Passkey` stores only the public key, one per device or synced keychain (iCloud/Google), discoverable (`resident_key: required`) so sign-in needs no email, always `user_verification: required`. `PasskeysController` (`/huella`, Configuración → «Entrar con huella») registers and removes them; `PasskeySessionsController` (`/sesion/huella`) signs in through the same `start_new_session_for` and `LoginAttempt` as the password; challenges live in the Rails session and are consumed once. `passkey_controller.js` converts base64url ↔ ArrayBuffer, shows passkey UI only where `isUserVerifyingPlatformAuthenticatorAvailable`, and on the sign-in page also offers it as autofill (`autocomplete="username webauthn"` + conditional mediation). After a password sign-in the first screen offers it once (`session[:offer_passkey]`, `passkeys/_offer`, «Ahora no» remembered per device in localStorage). The relying party is `Passkey.relying_party`: in production the host from `APP_HOST`/`RENDER_EXTERNAL_HOSTNAME`, else the request's. `User#revoke_password!` also deletes the account's passkeys; «Ver como» can't touch them. Sessions keep their 30/90-day limits; a passkey just makes signing back in one tap.

**Modo simple** (phone only, `users.simple_mode`, on by default, switch in Configuración → `SettingsController#simple_mode`; jóvenes don't have it yet, `User#simple_mode?`): below `md` a bottom bar (`shared/_bottom_nav`, `NavigationHelper#simple_bar_items`) replaces the drawer — Inicio, the role's own item (`simple_own_item`: their company, «Compañías», Logística, or the module of their logística area's flag), a center button (global search for `User#global_searcher?`, otherwise «Mi QR»), Agenda and «Más» (a bottom sheet with the rest of `nav_items` plus the badge scanner — for full access only Mi QR, the scanner, Alertas, Enfermería and Asistencia nocturna, `NavigationHelper::FULL_ACCESS_MORE_ITEMS` —, closed by tapping outside). The phone home shows the role's three figures (`DashboardFacade#simple_kpis`, links via `DashboardHelper#simple_kpi_url`) and only the stake and role charts (no link to the full dashboard: that stays on desktop or with simple mode off). Desktop never changes. Global search: `SearchesController` (`/buscar`) + `GlobalSearch` (people, companies, inventory items for inventory members, stakes/wards) + menu modules from `SearchesHelper#search_modules`.

**Novedades** (`ChangelogController`, `/novedades`, in the account menu): the app's changelog lives in `config/changelog.yml`, newest first, read by `ChangelogEntry` (no table). A user-visible feature or fix adds an entry there in the same change, written for the people who use it (optional `roles` narrows who sees it). `bin/docker-entrypoint` runs `novedades:anunciar` after `db:prepare`: each new entry becomes one `Alert` (`source: :novedades`, linking to its anchor in the page) exactly once, tracked by `AppSetting["changelog_announced_id"]` and also goes out as a push like any alert. Never change an entry's `id`.

**Historial** (`AuditLogsController`, `record_audit!` in the `Auditable` concern): each entry's `summary` is the full sentence (who did what to whom); `AuditLog::ACTION_KINDS` groups `action` values for the row icon and the "Acción" filter, and categories must match the module (participant fichas → `participantes`, never `asignaciones`). Updates log only real changes: `changed_field_labels` treats blank as nil and, for jsonb columns, takes a Hash of key → label so it names what changed inside ("teléfono", "alergias") — a form saved untouched must add nothing. Search is accent-insensitive over actor, target and summary (`translate()`, no extension).

**Enfermería** (`InfirmaryVisitsController` + `InfirmaryChartsController` + `InfirmaryNotesController`, nav "Seguimiento › Enfermería"): a live board (`broadcast_refresh_later_to "infirmary"`) of who is on the way, who is inside and who left. Access by flag: the logística area with `nursing` (`User#nursing_member?`, plus the superadmin = `infirmary_operator?`) admits, confirms arrivals, discharges and writes the chart; a joven's counselor or the auxiliar of their branch only announces "lo llevo" (`InfirmaryVisit.announce`, status `en_camino`) and may withdraw it before it arrives; every staff member sees the board (`infirmary_viewer?`), jóvenes don't. The clinical notes and the reason's detail are read only by nursing, the director couple and the joven's carers (`Authorization#can_read_infirmary_notes?`). `InfirmaryNote`s (a note or, with `medication`, a medicine given — picked from the infirmary inventory and discounted from it, see `.claude/rules/inventario.md` —, plus optional vital signs shown as pills) are append-only (`readonly?`), like inventory movements; board cards are wholly clickable via a stretched link (buttons sit above it with `relative z-10`). `InfirmaryNotifier` sends **one** shared alert (`Alert` audience `personas`, `recipient_ids`) to the joven's counselors and branch auxiliares when they enter, and again only if they leave home or to the hospital — never the clinical detail. A joven still inside comes pre-marked "ausente · Enfermería" in their night attendance list (`NightAttendancesController#set_in_infirmary`).

**Consejeros y su compañía:** a counselor's `participants.company_id` and their `Membership` in the company are kept equal from both sides (`Participant#sync_counselor_membership`, `Membership#place_counselor`/`unplace_counselor`); company pages, the organigrama and night attendance read the membership. A jóven's "Consejeros a cargo" comes from the company's staff, not the imported `person_in_charge` text.

**Reportes:** PDFs are built server-side with Prawn by plain Ruby classes in `app/reports/` — subclass `ApplicationReport` and implement `title`/`build`, which gets the letterhead, footer and table styling for free. `ReportsController` sends them inline so the browser prints them. Label sheets (`InventoryLabelsReport`, and `BadgeLabelsReport` for the lanyard badges: a front with name + company number (never its chosen name, set during the week) and a back with the QR of the participant's ficha, side by side) draw their own grid of dashed cut-lines instead of a table; the report gets its QR URL as a lambda from the controller since it doesn't know the routes. Bulk participant upload lives in `ParticipantImporter` (`roo`), which maps accent-insensitive Spanish headers onto attributes; add a spelling to `HEADERS` rather than asking anyone to rename a column. Note two pinned gems: `json` stays on 2.x (3.0 breaks `ActiveSupport::JSON.decode`, i.e. every jsonb column) and `roo` must stay ≥ 3.0 (2.x pulls a rubyzip with a path-traversal CVE, and we parse uploaded zips).

**Dashboard:** `DashboardFacade` (`app/facades/dashboard_facade.rb`) aggregates `Participant` class-method counts/groupings (by age, stake, role, gender, shirt size, jovenes vs. staff) for `DashboardsController` — add new KPI aggregations here rather than in the controller or view.

**Guía de estilo:** `DESIGN.md` is the visual source of truth (tokens in its frontmatter, rules in prose; `.impeccable/design.json` is its sidecar for Impeccable). New UI follows it: two page widths (`max-w-page`, `max-w-form`), the color rule (solid `cat-*-solid` only for key figures, the primary action and selected states; `/15` tints with `-ink` text for headings, categories and chips), the type scale (`text-meta/label/body/title/display/stat`, nothing under 11px), token radii and the three shadows. The shared pieces are ViewComponents: `PageComponent` (frame + intro/actions header, `width: :page|:form`), `IconTileComponent`, `StatTileComponent` (`size: :lg` solid / `:sm` tinted), `EmptyStateComponent`, `ChipComponent`, `SegmentedToggleComponent`; their colors come from one map, `Tones` (`app/components/tones.rb`). `section_heading` renders the tinted tile (`tone:`, optional block on the right). `test/lib/design_guardrails_test.rb` enforces it on every run: no raw Tailwind palette colors (dark mode uses the `muted`/`sunken` tokens), no `rounded-lg/xl/2xl/3xl` or `shadow-xl/2xl`, no arbitrary text size of 22px or less, no page with its own `px-4 md:px-8` wrapper instead of `PageComponent`, and every literal `icon "name"` must exist in `app/assets/svg/icons/lucide/outline` (a missing one breaks the page). Its exceptions are listed with their reason; adding one is a design decision.

**Frontend:** ViewComponents in `app/components/` (table, avatar, buttons, spans, info tiles) pair `.rb` + `.html.erb`. Stimulus controllers in `app/javascript/controllers/` (avatar fade-in, chart, confirm, dialog, mobile_menu, toast). Charts via ApexCharts (importmap pin with `preload: false`, imported on demand by `chart_controller.js` — same for jsQR in the scanners —, rendered from `data-chart-*` values; colors must be hex, see `ChartsHelper`), icons via Rails Icons (Lucide).

**Deploy:** Render free tier (Docker, `render.yaml` Blueprint) + Neon Postgres + Cloudflare R2 (Active Storage service `:cloudflare`, `aws-sdk-s3`) + Gmail via Apps Script; runbook in `docs/deploy_render.md`. With `R2_PUBLIC_URL` (the bucket's public domain) images render through `ApplicationHelper#storage_url` as direct bucket URLs instead of one Rails redirect per image; preload avatars with `with_attached_avatar` / `Participant::AVATAR_PRELOAD` so the processed variant keys come without extra queries. Render deploys `main` only after CI passes (`autoDeployTrigger: checksPass`) — there is no deploy job in the workflow. Production uses a single `DATABASE_URL`: cache/queue/cable live in their own Postgres schemas (`schema_search_path` in `config/database.yml`, created by `db:create_schemas`, which `lib/tasks/db_schemas.rake` hooks before `db:prepare`) so each keeps its own `schema_migrations`. Solid Queue runs inside Puma in `solid_queue_mode :async` (threads, not forked processes) to fit in 512 MB. `bin/docker-entrypoint` runs `db:prepare` on every boot; Thruster listens on `HTTP_PORT=10000`. The free tier has no shell, no persistent disk and sleeps after 15 min; one-off production tasks run from a local `RAILS_ENV=production DATABASE_URL=… bin/rails console`.
